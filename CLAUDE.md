# CLAUDE.md

Guidance for Claude when working in this repository.

## What this is

**Strawhenge Navigation** is a Unity package for character movement. It covers two ways of moving a humanoid character, plus the animation glue between them:

- **Destination** (AI / point-and-click): drives a `NavMeshAgent` to a target through a small state machine. It handles off-mesh links (jump across, drop down), "can't navigate right now" pauses, and result callbacks.
- **Locomotion** (direct control): a mover with walk/run/sprint, acceleration, turning, jumping with coyote time, gravity and fall detection. Animation-driven **pivots** (turn-on-the-spot / 180° turns) and **landings** are selected from data-driven profiles. The logic doesn't depend on how the character is moved: a **motor** does that (`CharacterController` and `Rigidbody` motors ship).
- **Movement sources + animation sync**: `IMovementSource` abstracts "whatever is moving the character right now". `MovementSourceManagerScript` picks the first active source, and `MovementAnimationSyncScript` feeds its velocity and events into an `Animator`.

The package is a work in progress. See "Known gaps" below.

Part of the Strawhenge family of packages (Common, FunctionalUtilities, Inventory, Interactions, ...). GitHub: `Strawhenge/Navigation`. The working branch is `master`; `origin/main` only holds the initial commit.

## Architecture notes

### Destination
- `DestinationScript` (MonoBehaviour) builds a `DestinationController` lazily on first access or in `Awake`, then ticks it from `Update`. Consumers use `destinationScript.DestinationController`.
- Public API: `GoTo(DestinationArgs)`, `Cancel()`, `IsLocationAccessible(...)`, `IsActive`, `CurrentVelocity`, `IsStrafing`, and the events `Activated/Deactivated/JumpBegan/JumpEnded/FallBegan/FallEnded`, plus the Animator requests `JumpTriggerRequested/PivotRequested/LandingRequested` and their `JumpTriggerCancelled/PivotCancelled/LandingCancelled`.
- Args come from `DestinationArgs.GoToExactly(loc)` / `GoToApproximately(loc)`, followed by builder calls (`WithSpeed`, `WithinDistance`, `Leisurely`, `Strafe`, `Callback`) and `Build()`. The extension methods in `DestinationControllerExtensions` are a shorter alternative.
- Every request ends with **exactly one** callback: `Arrived`, `Inaccessible`, `Cancelled` or `CancelledByNewDestination`. Keep this invariant whenever you touch the states.
- **Update state, then invoke callbacks.** Callbacks often call `GoTo` / `Cancel` straight away (e.g. a patrol going to its next waypoint), so `DestinationController` finishes every change first (`_current`, `_phase` through `Enter(...)` / `Stop()`, `_restartWhenSettled`) and runs callbacks last (`Finish`, `GoTo`, `Cancel`). Otherwise the nested call reaches the old state: the old request is called back again (endlessly, if its callback keeps redirecting) and the newest request is lost. Steering the `NavMeshAgent` for a redirect in place (`Phase.Redirect`, e.g. `Moving` setting the destination) happens after the previous request's callback, and only if the new request is still current (`ReferenceEquals(_current, args)` and the same phase). Setting the destination twice in one call chain leaves the agent heading for the first one.
- A redirect while moving (`Moving.Redirect`, as `Moving.CanRedirectInPlace` is always true) applies the new request's options in place (`Strafe` → `updateRotation`, `Leisurely` → `Agent.Enable` when the mode changes, speed, destination) so the agent keeps moving, rather than going back through `Preparing`. Any new request option must be applied in both places (`Preparing` and `Moving.Redirect`).
- Phases (`Phases/`) are plain classes deriving from `Phase`. They know nothing about requests: they never make callbacks or switch phase themselves. Each update `DestinationController` passes the current args (`_current`; null in a phase that can't be interrupted after its request was cancelled) and applies the `PhaseStep` they return: `Continue`, `To(PhaseId)` or `Finish(result)`. `Enter(args, strafe)` / `Exit()` bracket each phase; `CanRedirectInPlace` / `Redirect`, `OnAgentReactivated` and the Animator replies are the other hooks. `_phase` can outlive `_current`: a `Cancel` during a phase that can't be interrupted calls back straight away and clears `_current`, the phase (and any that follows it without a break, e.g. a jump's landing) finishes, then the controller stops. A `GoTo` meanwhile becomes `_current` straight away (the previous request is called back) and sets `_restartWhenSettled`.
- The `NavMeshAgent` stays **disabled** while idle and is enabled in `Preparing` through `Agent.Enable(leisurely)`, which also reserves an avoidance priority and applies the area-mask mode. Every `DestinationScript` shares `SingleAgentPriorityManager.Instance`. It's never cleared (clearing on scene unload broke additive scenes): slots are checked with Unity's `== null`, which is also true for destroyed agents, so their slots are reused automatically. Disabling `DestinationScript` mid-trip, on its own or by deactivating its GameObject, calls `Agent.Suspend()` (through `DestinationScript.OnDisable`), which pauses the trip: it disables the `NavMeshAgent` and frees its slot. `IsActive` stays true while paused. The controller isn't updated meanwhile, so the phase stays as it was. A `GoTo` while paused is applied on resume (`Moving.Redirect` doesn't steer a disabled agent), and a `Cancel` while paused leaves the agent disabled (`DestinationController.Resume` does nothing without a phase). Enabling it again calls `Resume()`, which enables the agent, reserves a slot again for the mode in use (`IsLeisurely`) and calls `Phase.OnAgentReactivated()` for a phase that can be interrupted, or sets `_restartWhenSettled` for one that can't. Unity resets a disabled `NavMeshAgent` (its path is lost), so `Moving` restarts the same request through `Preparing`, and jumps, drops, pivots and landings finish and then go through `Preparing`. A phase that relies on the agent's path must override `OnAgentReactivated`. This is separate from a `CanNavigate` pause (below).
- `Leisurely` gives low avoidance priority plus the "leisurely" area mask. `Strafe` sets `updateRotation = false`, and a strafing character keeps its facing through jumps. `IsStrafing` reports the request's `Strafe` option (`Phase.IsStrafing`), not `updateRotation`, which `Jumping` / `Falling` also turn off while they move the character by hand. `Agent.GetMode(leisurely)` is the single place a mode is chosen; `INavMeshAgentModes` only supplies the two `INavMeshAgentMode`s (area mask + `TryGetAreaCost`). `Agent.Enable` (and `Resume`) applies the mask and sets the cost of **all 32 areas**: the agent keeps costs it's given, so areas the mode doesn't override are reset to `NavMesh.GetAreaCost`. Off-mesh links are priced by their area (bake-generated links are in the built-in Jump area), so a mode prices jumps and drops through area costs. Costs are clamped to at least 1. `NavMeshAgent.Warp` resets the agent's area costs to the project's (the mask survives), so always warp through `Agent.Warp`, which re-applies the mode. `IsLocationAccessible` uses the same costs in its query filter. Without a modes asset, `DestinationScript` uses `FixedNavMeshAgentModes` with the NavMeshAgent's inspector mask.
- `IsLocationAccessible(location, leisurely = false)` queries the NavMesh directly (`NavMesh.SamplePosition` within one agent height, then `NavMesh.CalculatePath`) with the mode's area mask. It must never enable, move or reconfigure the agent, and only a **complete** path counts as accessible. (A `CanGoTo(DestinationArgs)` that also accepts partial paths for approximate requests may come later.)
- States must not leave lasting changes to the agent's own settings (e.g. `stoppingDistance`). `Moving` treats anything within `MinArrivalDistance` (0.1 m) as arrived when the stopping distance is smaller, since `remainingDistance` can stay just above 0.
- Jumps and drops along off-mesh links are moved by hand (`updatePosition = false`), using the destination settings.
- Destination settings (`Destination/Settings`) mirror the locomotion ones: `SerializedSource<IDestinationSettings, SerializedDestinationSettings, DestinationSettingsScriptableObject>` on `DestinationScript`, falling back to `DefaultDestinationSettings` with a warning. They hold `JumpSpeed`, `FallHorizontalSpeed`, `FallAcceleration`, `GroundLayers` (the layers `Falling`'s ledge check raycasts against; leave out the character's own colliders), `ApproximateSearchDistance`, and the animation settings: `StationaryPivots` / `MovingPivots` / `JumpLandings` / `FallLandings` (same profile types and `ProfileSources.Resolve` as locomotion), `DeferJumpTrigger` and `AnimatorWaitTimeout`. `DestinationController` reads them through `CachedDestinationSettings`, which passes values through and caches the profile lists. Both settings caches share `ProfileCacheVersion`, so `CachedLocomotionSettings.Invalidate()` (and `DestinationSettingsScriptableObject.OnValidate`) rebuilds both. `DestinationController` takes the settings as an optional argument, so tests can leave them out.
- Logging: `DestinationController` and its phases log through Common's `ILogger` (`Strawhenge.Common.Logging`), never `Debug.Log*`. `DestinationScript` has an optional `LoggerScript _logger`; without one it passes a `UnityLogger` on its GameObject. The controller requires a logger; tests pass a `FakeLogger`. Phases that log take it in their constructor. Add `using ILogger = Strawhenge.Common.Logging.ILogger;`, as `UnityEngine` has its own `ILogger`.
- **Can't navigate:** while `IDestinationContext.CanNavigate` is false (e.g. the character is ragdolled), `DestinationController.Update` switches to `Paused` (`Pause()`), which disables the agent as soon as it's entered (stopping it and freeing its slot). Once the character can navigate, it goes to `Preparing`, which warps the agent to where the character now is and calculates the path again; getting up off the NavMesh ends the trip as `Inaccessible`. `Moving` also hands over to `Paused` when the agent is disabled or off the NavMesh. The context is only read in `Update`, so a pause can start up to a frame after the consumer's state changes. `DestinationScript` takes a `DestinationContextScript` (`NullDestinationContext` without one); combining several reasons (ragdoll, stun, ...) is left to the consumer's script.
- Phases that can't be interrupted (`CanInterrupt == false`: jumps, drops, and the animation waits) always finish, unless the character can't navigate (below). A `GoTo` or reactivation meanwhile sets `_restartWhenSettled`, so the trip restarts through `Preparing` afterwards. One such phase can hand over to another (a jump to its landing) even after a cancel, and the run keeps the facing the first one started with (`Phase.Enter(args, strafe)`). A `CanNavigate` pause doesn't wait for the run: it abandons it straight away (its `Exit` still pairs `JumpBegan`/`JumpEnded` and `FallBegan`/`FallEnded`) and the trip restarts through `Preparing`, or, if the run's request was already cancelled, the controller stops. Abandoning a pivot or landing raises `PivotCancelled` / `LandingCancelled`, and a deferred jump still waiting for its trigger raises `JumpTriggerCancelled`, so whatever plays them drops them.
- The Animator's replies (`TriggerJump`, `CompletePivot`, `CompleteLanding`) reach `DestinationController` through `DestinationMovementSource` and are passed to the current phase (`Phase.OnJumpTriggered` / `OnPivotCompleted` / `OnLandingCompleted`); phases that aren't waiting ignore them.
- **Landings:** when a jump's arc ends, or a drop that actually fell (`FallBegan` raised) lands, `Jumping` / `Falling` ask `Landing.TrySetUp(...)` to match `JumpLandings` / `FallLandings` on the request's speed going into the link (`args.Speed`, kept from `Enter`; not the speed through the air, which is `JumpSpeed` / `FallHorizontalSpeed`) and the height dropped from take-off (`max(0, start.y - end.y)`). On a match they hand over to `Landing`, which stops the agent, raises `LandingRequested(id)` and waits for `CompleteLanding` or `AnimatorWaitTimeout` (warning once per ID, and raising `LandingCancelled`). `Jumping.Velocity` is measured from the per-update movement, like `Falling`'s.
- **Deferred jumps:** with `DeferJumpTrigger`, `Jumping` sets up the link, then waits at its start (velocity zero) after raising `JumpTriggerRequested` until `TriggerJump` arrives. Only then does it raise `JumpBegan` and move. On `AnimatorWaitTimeout` it warns once and launches anyway: unlike locomotion, it can't cancel, as the agent is already on the link.
- **Pivots:** never while strafing. `Preparing` matches `StationaryPivots` on the turn from the character's facing to the path's first corner (`GetCornersNonAlloc`) and the speed before its warp; `Moving` matches `MovingPivots` every update on the turn to `desiredVelocity` and the agent's speed. On a match they hand over to `Pivoting`, which stops the agent, turns off `updatePosition` / `updateRotation` (root motion plays the pivot), raises `PivotRequested(id)` and waits for `CompletePivot()` or `AnimatorWaitTimeout` (which raises `PivotCancelled`). Root motion has already turned the character, so it applies no turn of its own; it syncs the agent with `nextPosition` and goes back to `Moving`. A pivot that turned the character less than `PivotTurn`'s 1° suppresses pivots until the turn leaves every pivot's angle range, as in locomotion. While it plays, `Velocity` is the velocity coming in.

### Locomotion
- Consumers use `locomotionScript.LocomotionController`, as with `DestinationScript.DestinationController`: it's driven by `Move(Vector3 worldDirection)`, `Jump()` and the `Walk` / `Sprint` / `Strafe` flags, and has the events, `IsActive` / `IsActiveChanged` (following `LocomotionScript` being enabled) and the Animator replies (`TriggerJump`, `CompletePivot`, `CompleteLanding`). Locomotion is turned on and off through `LocomotionScript.enabled`.
- `LocomotionScript` is thin wiring, like `DestinationScript`: it resolves the motor, settings and logger, builds the `LocomotionController` (plain C#, holds all the logic and state) lazily on first access or in `Awake`, steps it, and calls its `internal` `Activate` / `Deactivate` from `OnEnable` / `OnDisable`. `Step` and `SetSettings` are `internal` too, and `BeginStep` / `EndStep` are explicit `ILocomotionStepper` implementations, so the controller's public API is only what consumers need. Logging goes through Common's `ILogger` (optional `LoggerScript _logger`, else a `UnityLogger`), never `Debug.Log*` in the controller.
- **Motors** (`Locomotion/Motors`): `ICharacterMotor` moves the character for the controller; `CharacterMotorScript` (abstract MonoBehaviour exposing `Motor`, like `MovementSourceScript`) plugs one into `LocomotionScript._motor`. The contract: `Velocity` is the velocity the last move achieved, read straight after it (the controller keeps it as `CurrentVelocity` through steps that don't move, so motors needn't); `IsGrounded` is as of the last move; `SetActive` follows `LocomotionScript` being enabled; `SetRotation` turns straight away (completed pivots); `Move(LocomotionStep, deltaTime)` moves by `step.Velocity` and turns to `step.Rotation`, and returns `MotorMoveResult.BlockedSideways`; `step.JumpStarted` is true on the one step a jump begins, so motors that snap to the ground let go (rather than guessing from upward speed). `UpdateMode` says when `LocomotionScript` steps the controller: `Update`, `FixedUpdate`, or `External` for a motor that implements `IExternallySteppedMotor` and calls `ILocomotionStepper.BeginStep` / `EndStep` from its own callbacks.
- Each step is two halves: `BeginStep(deltaTime)` (animator-wait timeouts, falling, rotation, speeds; reads the motor) returns a `LocomotionStep`, and `EndStep(result)` reacts to the move (`BlockedSideways` caps the speed). A step with `ShouldMove == false` (inactive, or a pivot playing) isn't passed to the motor. `Step(deltaTime)` runs both for `Update` / `FixedUpdate` motors.
- **Rigidbody motor** (`RigidbodyMotor` / `RigidbodyMotorScript`, settings through `IRigidbodyMotorSettings`, which the script implements from its serialized fields): a dynamic `Rigidbody` with an upright `CapsuleCollider` on the character's root (`RequireComponent`). It steps in `FixedUpdate` and sets the body's velocity. The controller owns gravity (`useGravity` off, rotation frozen, interpolation on, a frictionless material if none is set). Grounding is a sphere cast below the capsule within `GroundDistance` (or `GroundSnapDistance` while already grounded), on ground no steeper than `MaxSlopeAngle`; a step with `JumpStarted` leaves the ground (after it the snap distance no longer applies, and the jump is already past `GroundDistance`). While grounded, horizontal movement is redirected along the ground at the same speed, gaps over 0.02 m are snapped down, and `TryStepUp` lifts the body onto steps up to `StepHeight` it's about to walk into (sweep ahead, raycast for the top, overlap check). `BlockedSideways` comes from `OnCollisionEnter/Stay` contacts steeper than `MaxSlopeAngle` that aren't ceilings, and `Velocity` is the body's velocity, both from the physics step before the move (the body's own velocity is the one just set until physics runs). The script has `[DefaultExecutionOrder(100)]` so its `FixedUpdate` runs after `LocomotionScript`'s: a physics step with no move (a pivot playing) stops the body, as `LocomotionStep.ShouldMove` asks, apart from the pivot's root motion. Pivots need a `RootMotionRelayScript` (below) on the Animator's GameObject; the motor knows nothing about it, it just implements `IRootMotionHandler`. While active, the motor takes the root motion `MovementAnimationSyncScript` turns on for pivots (`TryApplyRootMotion`) and applies each frame's straight to the transform (horizontal movement and turn), as the CharacterController motor gets it. The first holds the body (kinematic, interpolation off, picking up the pose on screen) until the next move releases it from the transform. Driving the turn through the dynamic, interpolated body instead, whether as summed deltas or as rates, had the Animator (per frame) and physics (per step) fighting over the rotation, and it shook. While held, `Position` / `Rotation` read the transform. The Animator's built-in root motion would go through the body, which the motor holds still with rotation frozen, losing the turn. While the motor is inactive (Destination's pivots) it declines, and the relay hands back to `ApplyBuiltinRootMotion()`. Setups without pivots don't need the relay, so nothing is logged when it's missing (a pivot then doesn't turn the body); instead `RigidbodyMotorScriptEditor` shows a warning `HelpBox` in the inspector when the character has an Animator but no relay beside it, with a button that adds one with its `_motor` set, as one undo step. Turned off, the body is kinematic with its capsule and interpolation off (an interpolated body keeps writing its pose to the transform, fighting the `NavMeshAgent`); turned on, it picks up from the transform (Destination may have moved it).
- `CharacterControllerMotor` / `CharacterControllerMotorScript` keep the original `CharacterController` behaviour. While grounded the controller asks for no speed down (each motor keeps the character on the ground its own way), so the CharacterController motor pushes down while grounded and not rising: a `CharacterController` is only grounded after a move that pushes into the ground. The push is `GroundedPush` (default -2, a serialized field on its script, read through `ICharacterControllerMotorSettings`) or horizontal speed × tan(`slopeLimit`), whichever is stronger, so it follows any walkable slope or crest at speed instead of flying off (a fixed push couldn't keep up going downhill at a sprint). Pushing harder into the ground does nothing, as the `CharacterController` stops there; running off a ledge drops a few centimetres on the first frame. `LocomotionScript` finds its motor with `ComponentRefHelper.EnsureHierarchyComponent`; with none, it uses `NullCharacterMotor` and the character stays where it is.
- Coyote time is time since the motor was last grounded (`_timeSinceGrounded`), whatever the drop. Falling (`FallBegan`, fall landings) is separate and starts only after dropping `FallDistance`, so stairs and small bumps don't trigger it. Leaving the ground without jumping starts the downward speed at `FallStartSpeed` (default 2 m/s) rather than from still, the same for every motor; jumps are unaffected. Fall and jump landings match on the drop from the last grounded height to where the character lands (`_landingDrop`, measured before the landing step resets that height), like the destination's landings.
- **Airborne** means jumping, or falling once the character has dropped `FallDistance` (`LocomotionController.IsAirborne`), not just off the ground: stepping down stairs or a small drop and coyote time count as on the ground. No pivots play while airborne, and a stationary pivot queued on the ground is dropped. `AllowAirborneRotation` (default on) decides whether the character turns in the air; when off, it keeps its rotation (and the speed isn't limited for a sharp turn) and turns to the input once it lands. `AirborneMovement` decides the horizontal control in the air, with the ground speeds and acceleration: `Controlled` (default) as on the ground, `ControlledKeepsMomentum` the same but carrying on at its velocity while there's no input, `Momentum` none (carries on at the velocity it became airborne with). The carried velocity is `_momentum`, the horizontal velocity asked for in the last step that moved; a wall (`BlockedSideways`) sets it to what the move achieved, so it stops or slides. Slowing down in the air without input follows `_momentum`'s direction, not the facing. Control returns on landing.
- Settings come from `SerializedSource<ILocomotionSettings, SerializedLocomotionSettings, LocomotionSettingsScriptableObject>`, so they can be inline or an asset. If neither is set, `DefaultLocomotionSettings` is used. Both settings classes build their profile arrays with `ProfileSources.Resolve(...)`. It skips unset sources, and skips (with a warning) pivot or landing profiles whose `Id` is null, which means no pivot / landing asset is assigned. An incomplete profile never matches. Implementations must return null with an explicit `asset != null ? asset.Id : null` check: `asset?.Id` skips Unity's null check.
- The settings classes don't cache: their profile lists are resolved on every read. `LocomotionController` always reads settings through `CachedLocomotionSettings` (`LocomotionScript` wraps them), which passes values through and caches the four profile arrays. Profile ranges are `ValueRange` (see below), so matching (`PivotProfileExtensions.Matches` / `IsInAngleRange`, `LandingProfileExtensions.Matches`) allocates nothing. `OnValidate` on the settings asset, the pivot / landing profile assets and `LocomotionScript` calls `CachedLocomotionSettings.Invalidate()`, so in the Editor any edit rebuilds the lists on the next read; in builds they're resolved once. `LocomotionScript.OnValidate` also re-resolves its settings in play mode (swapped asset, edited inline settings), unless they were given through `SetSettings`.
- Ranges are `ValueRange` (`Runtime/Ranges`): a serializable struct with `Min`, `Max` and `Contains(value)` (inclusive; max below min contains nothing). Reading or checking it never allocates. `ValueRangePropertyDrawer` draws it on one line and warns when max < min. Its fields are `_min` / `_max`, the same as Common's `SerializedFloatRange`, so assets saved with that type keep their values. Don't use Common's `FloatRange` / `SerializedFloatRange` here: `FloatRange` is a class and `SerializedFloatRange.Value` allocates one on every read.
- Pivots are turned by root motion while they play, so `CompletePivot()` takes no rotation and applies none. Whether the pivot turned the character is measured from its rotation when the pivot started (`PivotTurn.DidTurn`: at least 1°), never read from the Animator's `deltaRotation`. When a pivot completes without turning (the pivot fallback, or a clip without root rotation), `LocomotionController` skips pivots until the turn leaves every pivot's angle range (`_suppressPivotsUntilTurned`) and turns normally. Otherwise the same pivot would match again every frame and the character would never turn.
- Pivots and landings are a handshake with the Animator. Locomotion raises `PivotRequested(id)` / `LandingRequested(id)` and blocks movement or rotation until `CompletePivot()` / `CompleteLanding()` is called back. Those calls come from `MovementAnimationSyncScript` via `PivotStateMachineBehaviour` / `LandingStateMachineBehaviour` (`OnStateMachineExit`).
- When `DeferJumpTrigger` is set, the jump waits for an animation event that calls `MovementAnimationSyncScript.OnJumpLaunch()` → `TriggerJump()`.
- While `LocomotionScript` is disabled, the Animator's completion calls go to whichever movement source is active instead, so they never arrive. `OnDisable` therefore calls `LocomotionController.Deactivate()`, whose `CancelAnimatorWaits()` clears the pivot, landing and jump-trigger waits (and any queued stationary pivot or jump not yet applied). Any new "wait for the Animator" flag must be reset there too.
- `LocomotionToggleScript` turns `LocomotionScript` off while the destination controller is active, or when a `BaseLocomotionToggleConditionsScript` says so. It applies the starting state in `Start` (after every `Awake`), then follows the change events.

### Animation contract
`MovementAnimationSyncScript` expects these Animator parameter names (see `AnimatorParameters`): `Move Speed`, `Strafing`, `Strafe X`, `Strafe Y`, `Falling`, `Jump`, `Jumping`, `Pivot`, `Pivot ID`, `Pivot Right Foot`, `Landing ID`, `Land`. The controller must contain a `PivotStateMachineBehaviour` and a `LandingStateMachineBehaviour`. `Assets/Development/Character.controller` is the reference setup. Renaming a parameter breaks every consumer's controller. Character-relative values (`Strafe X` / `Strafe Y`, `Pivot Right Foot`) are measured against the Animator's transform, never `transform.root`, so characters can sit under a parent object.

**`RootMotionRelayScript`** (optional, on the Animator's GameObject, `RequireComponent(Animator)`): implements `OnAnimatorMove` and hands the Animator's root motion to the character's motor while `applyRootMotion` is on, if the motor is an `IRootMotionHandler` (`TryApplyRootMotion(deltaPosition, deltaRotation)`; the rigidbody motor is, the CharacterController motor isn't). Its optional `_motor` (a `CharacterMotorScript`) is found in the parents if not set, and the handler is resolved once in `Awake`. When the motor isn't a handler, or declines, it calls `ApplyBuiltinRootMotion()`, so characters behave as without it. While `applyRootMotion` is off it does nothing: `ApplyBuiltinRootMotion()` applies root motion regardless of that flag, and on a Rigidbody the idle or walk clip's root motion would end up in the body's velocity and keep it moving. Having `OnAnimatorMove` anywhere on the Animator's GameObject turns off the Animator's built-in root motion, so keep it in this one component.

Setup problems never crash and never leave locomotion waiting for an animation that can't happen. `MovementAnimationSyncScript` warns once in `Awake` and falls back:
- **No Animator:** movement plays without animation, and a deferred jump triggers straight away.
- **No pivot or landing behaviour:** that request is completed straight away (a pivot without turning).
- **Non-humanoid rig:** no foot bones, so `Pivot Right Foot` stays false.

Two timeouts stop a pivot, landing or deferred jump from waiting forever. Both are serialized fields, so they can be tuned per character:
- **`MovementAnimationSyncScript._animationStartTimeout` (0.3 s):** the pivot or landing animation must *start* in this time. The behaviours raise `Started` from `OnStateEnter`, not `OnStateMachineEnter`, which transitions straight to a state skip. Otherwise it's skipped: the trigger is reset, root motion turned off, the request completed (a pivot without turning), and a warning logged once per ID. This is the usual "no transition for this ID" case. It only counts while the Animator is active. When `MovementSourceManagerScript.ActiveSourceChanged` fires, everything set on the Animator for the old source is dropped as if it had cancelled it: a pivot or landing (started or not, root motion off, its end ignored), the `Jump` trigger, and the `Jumping` / `Falling` flags (`LocomotionScript.OnDisable` doesn't end a jump or fall in progress). When the movement source raises `PivotCancelled` / `LandingCancelled` / `JumpTriggerCancelled`, the sync script resets that trigger and (for a pivot) turns root motion off, whether or not the animation has started, and ignores the animation's end if it still plays out. Movement sources never mention the Animator: these events only say a request is no longer wanted (`LocomotionMovementSource` never raises them).
- **`LocomotionScript._animatorWaitTimeout` (2 s):** a safety net in locomotion itself (`LocomotionController`), for waits nobody completes (no sync script, nothing wired up, an animation that never finishes). Pivots and landings are completed, a deferred jump is **cancelled** rather than launched late, and a warning is logged. It must be longer than the longest pivot or landing clip.

## Code conventions

Follow the existing style. The ReSharper settings are in `Strawhenge.Navigation.Unity.sln.DotSettings`.
- Leave out `private`/`internal` where they're the default (`readonly Foo _foo;`, `class Agent`).
- No empty `if` / `else` / loop blocks, not even with a comment: invert the condition, or extract a method (e.g. `LocomotionController.HandlePivots`). Deliberately empty member bodies (private constructors, null objects, no-op virtual hooks) are fine.
- Serialized fields are `[SerializeField] T _camelCase;`, never public fields. Expose them through get-only properties.
- **One type per file**, named after the type (`FakePivotProfile.cs` holds `FakePivotProfile`). Don't put several classes, interfaces or enums in one file, and don't nest classes inside other classes. The only exceptions are partial-class files: a private implementation type kept in its own file, as `DestinationArgs.Builder.cs` does for `DestinationArgs.ArgsBuilder`, and a script's test hooks in `<Type>.Setup.cs` (see Testing).
- Naming suffixes: `...Script` for MonoBehaviours, `...ScriptableObject` for ScriptableObjects, `Serialized...` for `[Serializable]` inline equivalents. Interfaces sit behind all three (`IPivotProfile`, `ILandingProfile`, `ILocomotionSettings`).
- Null objects: `NullX` with `static Instance { get; } = new();` and a private ctor, used instead of null checks (`NullDestinationContext`, `NullMovementSource`). When "nothing" still has to return a value, use a fallback that keeps the existing behaviour instead (e.g. `FixedNavMeshAgentModes` with the agent's own area mask).
- Resolve component references with `ComponentRefHelper.EnsureHierarchyComponent` / `EnsureRootHierarchyComponent` from Common. Warn with `Debug.LogWarning(..., this)` and fall back to defaults rather than throwing.
- Keep logic in plain C# classes and keep MonoBehaviours as thin wiring. Use `internal` for things only the package needs (e.g. `DestinationController.Update`).
- Namespaces: `Strawhenge.Navigation.Unity` for most code, `Strawhenge.Navigation.Unity.Destination` for the Destination folder, `...Unity.Editor` for the editor. Folders below that level don't add namespace segments, so ignore the CheckNamespace warning.
- Usings are not sorted System-first. The language level is the one Unity 2021.3 supports (C# 9: `new()`, `??=` and `is not` are fine; C# 10+ features like file-scoped namespaces and global usings are not).
- Avoid per-frame allocations: reuse `NavMeshPath`; use `NavMeshAgent.pathStatus`, not `path.status` (the `path` getter allocates); read settings through `CachedLocomotionSettings`, never the settings classes directly; use `ValueRange`, not Common's `FloatRange`; no LINQ or lambdas in per-frame code.
- Commit messages are lowercase, in the form `area; what changed`, e.g. `refactor locomotion settings; ...`.

## Working safely in a Unity project

- **Every asset and script has a `.meta` file holding its GUID.** When you move or rename a `.cs` file, move or rename its `.meta` along with it. Without that, references in scenes, prefabs and assets break silently. For new files Unity generates the `.meta` on import, so don't invent one.
- **Renaming a `[SerializeField]` field drops the data saved in existing assets** (`.asset`, `.unity`, `.controller`). Add `[UnityEngine.Serialization.FormerlySerializedAs("_old")]`, or tell the user the assets must be re-assigned.
- Renaming or moving a MonoBehaviour/ScriptableObject class is safe only if the file name still matches the class name and the `.meta` goes with it.
- Don't edit `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` or the generated `*.csproj`/`*.sln` files. They're regenerated (and git-ignored).
- Hand-edit YAML assets (`.unity`, `.controller`, `.asset`) only when you have to, and keep the change minimal.
- Nothing can be compiled or run outside the Unity Editor here. After a change, ask the user to let Unity recompile, check the Console and run the tests (see Testing). For manual checks, use `Assets/Development/Scenes/Main.unity`. The `DestinationScript` inspector has play-mode buttons (GoToExactly / GoToApproximately / IsLocationAccessible / Cancel), and the `LocomotionScript` inspector shows its controller's private fields live. The `RagdollScript` inspector has Ragdoll On / Off buttons, and `DevelopmentDestinationContextScript` a Cannot Navigate checkbox, for testing `CanNavigate` pauses.
- Package code must not reference anything in `Assets/Development`. Dependencies flow Development → Package only.

## Testing

PlayMode tests live in `Assets/Package/Tests/` (asmdef `Strawhenge.Navigation.Unity.Tests`). The user runs them from **Window → General → Test Runner → PlayMode → Run All**. Claude can't run Unity, so ask the user for the results.
- The asmdef follows Common's test assembly: `UNITY_INCLUDE_TESTS` define constraint (projects that consume the package don't compile it), `overrideReferences: true`, and precompiled `nunit.framework.dll`, `Strawhenge.Common.dll` and `FunctionalUtilities.dll`. It also references the `Strawhenge.Common.Unity` asmdef (e.g. for `AnimatorParameter`, the type of `AnimatorParameters`' fields).
- Build objects in code rather than loading scenes or prefabs. Create the GameObject inactive, add its components, configure them, then activate it so `Awake` sees the configuration. Destroy everything in `[UnityTearDown]` and wait a frame.
- Test hooks are `internal` and exposed through `Runtime/AssemblyInfo.cs` (`InternalsVisibleTo`). They live in a partial-class file next to the script, `<Type>.Setup.cs`, with any field that only a hook sets (e.g. `_settingsOverride`, `_loggerOverride`, `_modesOverride`), so the main file lists only real configuration and state. A hook that sets a serialized field (`SetMotor`, `SetNavMeshAgent`, `SetAnimator`) leaves that field in the main file. `LocomotionScript.Setup.cs` has `SetMotor(...)`, `SetSettings(...)` and `SetLogger(...)`; `Awake` keeps what was already set. `CharacterControllerMotorScript.Setup.cs` has `SetCharacterController(...)`, called before `Motor` is first read. `DestinationScript.Setup.cs` has `SetNavMeshAgent(...)`, `SetModes(...)`, `SetSettings(...)` and `SetLogger(...)`, which must be called before `Awake`. `MovementAnimationSyncScript.Setup.cs` has `SetAnimator(...)`, `SetMovementSourceManager(...)` and `SetBehaviours(pivot, landing)` (behaviours made with `ScriptableObject.CreateInstance`, since the test controller has no pivot or landing states; tests call their `OnStateEnter` / `OnStateMachineExit` to play the Animator's part), and `MovementSourceManagerScript.Setup.cs` has `SetMovementSources(...)`. Set every reference a script would otherwise warn about, so test runs don't fill the Console with setup warnings meant for scenes. Add similar small hooks rather than using reflection.
- Fakes go in `Tests/Fakes/` and setup helpers in `Tests/Helpers/`, one per file, even when only one test class uses them. Test classes hold only their tests and private setup methods. Current fakes: `FakeLocomotionSettings` (defaults to `DefaultLocomotionSettings`, so each test sets only what it needs), `FakeDestinationSettings` (likewise, from `DefaultDestinationSettings`), `FakePivotProfile`, `FakeLandingProfile`, `FakeNavMeshAgentModes` / `FakeNavMeshAgentMode` (area mask, plus `WithAreaCost`), `FakeLogger` (writes to the test output and records messages for assertions; `LogError` / `LogException` fail the test), `FakeDestinationContext` (settable `CanNavigate`), `FakeMovementSource` / `FakeMovementSourceScript` (a movement source driven by hand: settable `IsActive`, `RequestPivot` / `RequestLanding` / `RequestJumpTrigger`, `BeginJump` / `BeginFall`, `CancelPivot` / `CancelLanding` / `CancelJumpTrigger`, and records the completions it gets), `FakeMotor` (an `ICharacterMotor` without physics: moves exactly as told onto a flat floor at a settable `GroundHeight`, null for none, and is grounded on it; settable `BlockedSideways` / `HorizontalFreedom` to play a wall; `ForgetVelocity()` to play a motor that reports none while not moved; records every move). Assert on a `FakeLogger` rather than `LogAssert` for anything the destination or locomotion controller logs. Physics tests that should hold for every motor take a `TestMotor` (`CharacterController` / `Rigidbody`) as a fixture argument (`[TestFixture(TestMotor.CharacterController)]` / `[TestFixture(TestMotor.Rigidbody)]`) and pass it to `LocomotionTestCharacter.Create(..., motor: ...)`; read grounding through the motor (`GetComponent<CharacterMotorScript>().Motor.IsGrounded`), and wait for conditions rather than a single frame, as the Rigidbody motor steps in `FixedUpdate`. `RigidbodyMotorTests` covers its ground, slope, wall and step handling. Current helpers: `LocomotionControllerHarness` (a `LocomotionController` on a `FakeMotor` with a `FakeLogger`, already active, stepped by hand at a fixed frame time with `Step` / `StepFor` / `StepUntil`; controller tests use plain `[Test]`s and need no GameObjects, physics or tear-down), `LocomotionTestCharacter.Create(...)`, `DestinationTestCharacter.Create(...)` (a `NavMeshAgent` + `DestinationScript` set up in full), `TestNavMesh.Build(...)` / `TestNavMesh.Box(...)` (a NavMesh from flat boxes; older destination tests still build theirs inline). `TestAnimatorController.Create()` (an in-memory Animator controller with the parameters in `AnimatorParameters` and one empty state, built with `UnityEditor.Animations` in the Editor, so an Animator in a test doesn't warn "Animator is not playing an AnimatorController"; it has no pivot or landing states).
- Assert behaviour through public API and events (position, `PivotRequested`, `JumpBegan`, ...), not private fields. Check that each test's setup worked ("Setup failed: ..."), and back any "doesn't happen" assertion with a baseline test showing it does happen normally.
- Bug-fix workflow: put the failing tests on a `test/...` branch (PR into `master`), and the fix on a `fix/...` branch from it (PR into the test branch). Merge the fix PR first, then the test PR, so `master` never has failing tests.
- Unity generates `.meta` files for new files and folders. Commit them once Unity has imported the files; don't hand-write them.

## Git workflow

- Work on a branch and open a pull request for the user to review. Don't merge it yourself.
- The repo stores LF line endings, and Windows checkouts use `core.autocrlf=true`, so files on disk are CRLF. Some files have a UTF-8 BOM. Preserve both when editing.
